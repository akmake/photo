# תחום א' — אכיפת רישיון, תקשורת ואבטחת-תוכנה

## א.1 חמשת המצבים של האפליקציה

האפליקציה נמצאת תמיד באחד מחמישה מצבים. המצב נקבע במנוע (`engine/server.py`),
לא ב-UI, כי ה-UI נעקף בקלות.

| מצב | מתי | מה עובד |
|---|---|---|
| **לא-מופעל** (UNACTIVATED) | אין פתק שמור | רק מסך כניסה. שום כלי, שום אלבום |
| **פעיל** (ACTIVE) | פתק תקף, מנוי בתוקף, בתוך חלון אופליין | הכל |
| **מיושן** (STALE) | חלון האופליין עבר, לא הצליח לרענן (אין רשת) | נעול. "התחבר לאינטרנט לרגע" |
| **נעול** (LOCKED) | השרת אמר: מנוי פג / רישיון בוטל | נעול. "חדש מנוי" |
| **בחסד-תשלום** (DUNNING) | תשלום נכשל אך בחלון החסד | עובד, עם התראה |

מעברים: לא-מופעל →(כניסה+הפעלה)→ פעיל →(עבר חלון בלי רשת)→ מיושן →(רענון מוצלח)→ פעיל.
פעיל →(השרת: מנוי פג/בוטל ברענון)→ נעול.

## א.2 שני השעונים — התשובה ל"מתנתק וממשיך"

בכל פתק חתום יש שני תאריכים:

- **`expires_at`** — סוף תקופת המנוי. האמת של השרת.
- **`offline_until`** — `issued_at + חלון_אופליין` (ברירת מחדל 14 יום).

הזמן שמותר לעבוד = **המוקדם מבין השניים**. כשעובר — המנוע מסרב.

**התשובה הישרה לתרחיש שלך:** מי שמתנתק וממשיך לעבוד יכול לעשות זאת **עד סוף חלון
האופליין — לכל היותר 14 יום מהרענון האחרון** — ולא לנצח. זה מכוון: צלם בחתונה בלי
קליטה חייב לעבוד. אחרי 14 יום בלי רענון אחד → מיושן → נעול. **חלון-החשיפה המקסימלי
שווה במדויק לאורך חלון-האופליין**, וזו הכפתור שאתה מכוון (§א.10).

הרענון (כשיש רשת) דוחף את שני התאריכים קדימה. אז משתמש לגיטימי לא מרגיש כלום;
רק מי שמתנתק בכוונה סופר לאחור.

## א.3 הגנת שעון — שלא יחזירו את התאריך אחורה

בלי זה, כל אחד היה מזיז את שעון Windows אחורה ונשאר בחלון לנצח. ההגנה:

1. **סימון-זמן עולה (high-water):** האפליקציה שומרת את *הזמן הכי מאוחר שראתה אי
   פעם*. בכל הפעלה ובכל קריאה למנוע: אם `now < high_water − סטייה(2 דק')` →
   השעון הוחזר → מצב מיושן, דורש רענון אונליין.
2. **בשני מקומות לפחות:** הסימון נשמר גם בקובץ תחת `LOCALAPPDATA` וגם ברישום
   (registry), ולוקחים את המקסימום. מחיקת אחד לא מאפסת.
3. **מול הפתק:** `now` חייב להיות `≥ issued_at − סטייה`. פתק "מהעתיד" נפסל.
4. **קדימה לא עוזר לפורץ:** הזזת השעון קדימה רק *מקדימה* תפוגה. אין תמריץ.

**הגבול הישר:** מי שמוחק את *כל* המצב המקומי (קובץ + רישום) וגם חוסם רשת — מאפס את
הסימון. אבל אז אין לו פתק, והוא מגיע ל-`offline_until` בלי יכולת לרענן → נעול.
ומחיקת-מצב = חייב להתחבר מחדש = השרת בודק מנוי = נתפס. אין דרך חינם.

## א.4 השוער במנוע — איפה האכיפה יושבת פיזית

- ב-`engine/server.py` נכנס **שומר אחד** לפני כל נקודת-קצה של "עבודה": עריכה,
  ריטוש, ריצת-מתכון, ייצוא, אלבום, גזירת-גלריה.
- השומר בודק, **בלי רשת**, פתק מאומת מקומית: חתימת Ed25519 (מפתח ציבורי מוטמע)
  + התאמת מכשיר + תוקף + סימון-שעון. עובר → ממשיך. נכשל → 402/403 + סיבה.
- נשארים **פתוחים תמיד:** `/health`, סטטוס-רישיון, וקצות הכניסה/הפעלה.
- ה-UI מציג מסך נעילה יפה, אבל **הסירוב האמיתי במנוע** — עקיפת המסך לא נותנת כלום.

## א.5 טביעת-האצבע של המחשב (device_id)

- **מקור:** `MachineGuid` של Windows (מהרישום, `HKLM\...\Cryptography`). יציב
  לאורך אתחולים, התקנות-מחדש של האפליקציה ועדכונים. משתנה רק בהתקנת-מחדש של המערכת.
- **לא כרטיס-רשת/MAC** — משתנה עם VPN, תחנת-עגינה, מתאם USB, ושובר רישיון תקין.
- **מה נשלח לשרת:** `SHA256(MachineGuid + מלח-אפליקציה)` — לא הגלם. השרת אף פעם לא
  רואה מזהה-חומרה גולמי.
- **מכסת מכשירים** נאכפת בשרת בהפעלה (`max_devices` לכל רישיון). מכשיר מעבר למכסה → 409.
- **שיבוט VM:** שכפול יביא אותו MachineGuid → נתפס במכסה. זיהוי-VM ייעודי = הקשחה עתידית.

## א.6 פרוטוקול הרענון והתקשורת

- **מתי מרעננים:** בהפעלה (אם יש רשת ועבר זמן מהרענון האחרון), ובכל N שעות ברקע.
- **קריאה:** `POST /licenses/refresh {device_id}` עם אסימון-חשבון. מחזיר: פתק חדש /
  403 (בוטל/פג) / 409 (המכשיר נותק במקום אחר).
- **הצפנה:** הכל TLS ל-VPS בייצור. בפיתוח localhost.
- **אסימון-החשבון (JWT)** נשמר **מוצפן** (DPAPI של Windows), לא כטקסט גלוי.
- **חתימה נגד זיוף:** הפתק חתום Ed25519 — גם MITM לא יכול לזייף פתק (אין לו מפתח
  פרטי). הוא *יכול* להעלים תשובת "בוטל", אבל `offline_until` חוסם את זה ל-14 יום.
- **replay:** בפתק יש `issued_at` ו-nonce; האפליקציה מעדיפה תמיד את הפתק החדש ביותר.

## א.7 מחזור-חיים מלא של מנוי (כל מצב, מה קורה)

| אירוע | התנהגות |
|---|---|
| הפעלה ראשונה בלי אינטרנט | לא ניתן להפעיל. מסך: "צריך חיבור פעם אחת להפעלה" |
| אינטרנט נופל תוך כדי עבודה | ממשיך עד `offline_until`; רענון-רקע מנסה בשקט |
| ביטול מנוי לפני סוף התקופה | `is_current` נשאר עד סוף התקופה; בסוף → רענון מחזיר "פג" → נעול |
| מנוי פג בזמן שהמשתמש אופליין | עובד עד `offline_until` (≤14 יום), ואז נעול |
| תשלום נכשל (dunning) | `past_due` → פתק לחלון-חסד קצר (למשל 7 ימים) ואז נעול |
| החלפת מחשב | ניתוק הישן (משחרר מקום) → הפעלה בחדש |
| מחיקת קובץ הפתק | אין פתק → חייב כניסה/הפעלה (רשת) → נתפס |
| התקנת-מערכת מחדש | MachineGuid משתנה → נראה מכשיר חדש → מכסה |
| החזרת שעון | נתפס ב-high-water (§א.3) |

## א.8 הקשחת הבינארי (שלא יפרקו ויעקפו את השוער)

- **Nuitka** למנוע — קימפול למכונה, בלי bytecode קריא. (היום PyInstaller = מתפרק).
- **חתימת קוד** ל-EXE (תעודת OV ~$99/שנה) — בלי זה SmartScreen מפחיד בהתקנה.
- **ASAR integrity** + fuses (`OnlyLoadAppFromAsar`, `EnableEmbeddedAsarIntegrityValidation`)
  — שינוי הקובץ עוצר את האפליקציה.
- **המפתח הציבורי** יושב בתוך הבינארי החתום — שינויו שובר את החתימה.

## א.9 הרובד הבלתי-שביר (החלטה שלך, לא חובה עכשיו)

כל §א.1–א.8 מייקר פריצה אבל לא מונע אותה מוחלטית, כי הכלים רצים על המחשב שלו.
**הדבר היחיד שלא ניתן לפרוץ הוא יכולת שרצה אצלך בשרת.** מומלץ לבחור יכולת-דגל אחת
(מועמדות: **ייצוא סופי לדפוס**, או **"המוח" של האלבום החכם**) ולהריץ אותה בשרת מול
מנוי בתוקף. פורץ שעקף את השוער יקבל תוכנה *שבורה* — האלבום/הייצוא פשוט לא ירוצו.
מתנגש עם עקרון "החישוב על המשתמש" ב-`ARCHITECTURE.md`, אז לרישוי-בלבד העומס זניח,
אבל העברת חישוב-כבד לשרת = החלטה כלכלית נפרדת.

## א.10 הכרעות-מוצר בתחום הזה (רק אתה יכול)

1. **אורך חלון-האופליין** — 14 יום (איזון), 7 (מחמיר), 30 (נוח). = חלון-החשיפה המקסימלי.
2. **חלון-חסד-תשלום (dunning)** — כמה ימים עובדים אחרי שכרטיס נכשל לפני נעילה.
3. **רובד בלתי-שביר (§א.9)** — כן/לא, ואיזו יכולת מעבירים לשרת.
4. **תקופת ניסיון (§א.11)** — אורך הניסיון, והאם מלא-יכולות או מוגבל.

## א.11 תקופת ניסיון

ניסיון חינם בהרשמה — הדרך שהצלם מתנסה לפני שמשלם. מתלבש **בדיוק** על המנגנון הקיים:
מצב `trialing` הוא כבר מצב-מנוי-בתוקף לכל דבר (`is_current()` מכיר בו), אז הניסיון
מנפיק פתק חתום רגיל, השוער במנוע מתייחס אליו כמו למנוי פעיל, וחלון-האופליין חל עליו.

### א.11.1 מה קורה, שלב-שלב

| אירוע | התנהגות |
|---|---|
| הרשמה (מייל או גוגל) | נפתח מנוי `trialing`, `plan="trial"`, `provider="trial"`, `current_period_end = עכשיו + ימי_ניסיון` (ברירת מחדל 14). **בלי כרטיס אשראי** |
| שימוש בזמן הניסיון | הכל עובד כמו מנוי משלם (או מוגבל — §א.11.3). פתק חתום, אכיפה רגילה |
| הצלם רוכש בזמן הניסיון | המנוי עובר ל-`active`, תקופה חדשה בתשלום |
| הניסיון נגמר בלי רכישה | השרת: `is_current` נעשה שקר → ברענון הבא נעול, מסך "הניסיון הסתיים — לרכישה" |
| הניסיון נגמר בזמן אופליין | עובד עד `offline_until` (≤ חלון-האופליין), ואז נעול — כמו כל מנוי |

### א.11.2 מניעת ניצול (trial abuse) — לרמות הקטנות

הבעיה: להירשם שוב ושוב עם מיילים חדשים ולקבל ניסיון אינסופי.

- **שכבה 1 — לפי מייל:** ניסיון אחד לכל חשבון. טריוויאלי לעקוף עם מייל חדש — לכן לבד לא מספיק.
- **שכבה 2 — לפי מכשיר:** בהפעלה הראשונה על מחשב, השרת רושם את טביעת-האצבע
  (`device_id` המגובב, §א.5) בטבלת "מכשירים שכבר מיצו ניסיון". מכשיר שכבר מיצה
  ניסיון → הרשמה חדשה עליו לא מקבלת ניסיון חדש, אלא ישר "צריך מנוי".
- **שכבה 3 — הגנת שעון:** הארכת ניסיון בהחזרת-שעון נחסמת ב-high-water (§א.3).
- **הגבול הישר:** מחשב חדש + מייל חדש = ניסיון חדש. זה מקובל בכל התעשייה; לא מנסים
  לסגור אותו הרמטית, רק לחסום את הניצול הקל (אותו מחשב, שוב ושוב).

### א.11.3 יכולות בזמן הניסיון — הכרעה שלך (§א.10.4)

שתי גישות, שתיהן נפוצות:
- **מלא-יכולות** (מומלץ להמרה): הצלם חווה את המוצר האמיתי. פשוט לבנות. סיכון: "יסחט"
  פרויקט אחד ויעזוב.
- **מוגבל:** למשל ייצוא עם סימן-מים, או תקרת גלריות/אחסון נמוכה. ממיר פחות אבל
  מגן מ"שימוש חד-פעמי". דורש דגלי-יכולת בפתק ובשוער.

### א.11.4 נגזרת קוד (קטן)

היום `POST /auth/register` **לא** יוצר מנוי. השינוי: בהרשמה נפתח מנוי `trialing`
עם תפוגה, ונבדק שהמכשיר לא מיצה ניסיון (שכבה 2 נאכפת בהפעלה הראשונה, לא בהרשמה,
כי המכשיר נודע רק אז). כל השאר — השוער, הפתק, חלון-האופליין — כבר קיים ולא משתנה.

# תחום ב' — אחסון: הפּוּל, המכסות, הספירה והאכיפה

## ב.0 העיקרון הכלכלי — למה אחסון כמעט חינם כאן

**רק תצוגות עולות, לא הגלם** (`CLIENT-GALLERY.md`): `preview` ~350KB + `thumb`
~35KB לתמונה. חתונה של 600 פריימים ≈ **0.25GB**. כלומר:

| קונים | מכיל בערך |
|---|---|
| 5TB | ~20,000 חתונות של תצוגות |
| 1TB | ~4,000 חתונות |

המסקנה: המכסות יכולות להיות **נדיבות מאוד** בלי סיכון עלות, כי המקור הכבד לעולם לא
עולה. האחסון הוא מרכיב-עלות שולי מול ההכנסה, לא צוואר-בקבוק.

### ב.0.1 שני סוגי עלות — אחסון קבוע, הורדות משתנות

- **אחסון** = הג'יגות ששוכבות. קבוע, חודשי, וזעום (למעלה).
- **הורדות (egress)** = בכל צפייה של לקוח/אורח בגלריה, הדפדפן שלו מוריד את הקבצים.
  זה המרכיב ה**משתנה**, לפי כמה צופים. אבל גם הוא קטן: 100 צפיות בסט תמבניילים ≈ 2GB
  = סנטים גם אצל ספק יקר, ו**אפס** אצל ספק עם הורדות-חינם. CDN עוד מקטין (צופה שני
  מקבל מהמטמון). **המסקנה: בוחרים ספק עם הורדות-חינם, והמרכיב המשתנה נעלם.**

## ב.1 הספק — Cloudflare R2 (הוכרע)

**אין "פּוּל שקונים ומחלקים".** זו תפיסה של אפליקציית-צריכה. אחסון-אובייקטים אמיתי
הוא **תשלום-לפי-שימוש**: משלמים חודשית לפי הג'יגות שבאמת יושבות, לא על בלוק שנקנה
מראש. מחקת — הפסקת לשלם. לכן המכסות שלנו הן כלי **מוצרי** (הוגנות ודרגות חבילה), לא
חלוקה של משהו קנוי. **העלות גדלה יחד עם ההכנסה, אף פעם לא לפניה.**

**הספק שנבחר: Cloudflare R2.** שלוש סיבות:
1. **הורדות (egress) חינם לגמרי** — מנטרל את הפריט היחיד שיכול להפתיע (§ב.0.1).
2. **CDN מובנה** — ספק אחד = אחסון + מהירות + הורדות-חינם. אין לחווט שני ספקים.
3. **בלי מינימום, תואם-S3** — מתחילים בעלות ~אפס, משלמים על מה שיושב, ו-`gallery_store.py`
   כבר יודע S3 (שורת-קונפיג).

האחסון יקר-יותר לטרה (~$15) אבל אצלנו זעום, אז ההפרש לא רלוונטי; הפשטות שווה יותר.
**רשת ביטחון:** בקנה-מידה גדול אפשר לעבור ל-**Backblaze B2 מאחורי Cloudflare** —
אותן הורדות-חינם, פחות עלות-אחסון — במעבר של שורת-קונפיג. לא ננעלים.

**המקור (RAW) לעולם לא עולה. iDrive Personal / תוכניות-גיבוי — לא רלוונטיות** (אי
אפשר לחלק בין דיירים ולא להגיש דרך API).

## ב.2 מודל הנתונים (תוספות)

- **Plan**: `storage_gb` (מכסה), `max_devices`, `features`.
- **חשבון**: `storage_used_bytes` (מונה רץ), `storage_quota_bytes` (מהחבילה;
  אדמין יכול לדרוס פרטנית).
- **StorageLedger** (רשומות append-only, אופציונלי): כל אירוע העלאה/מחיקה עם גודל,
  לביקורת ולהתאמה מול השימוש האמיתי בדלי.

## ב.3 נקודות אכיפה (לרמות הקטנות)

- **בהעלאה** (preview/thumb): לפני שמירה — `used + נכנס ≤ quota`? לא → `413`
  "האחסון מלא, שדרג חבילה". הגודל נמדד מהבייטים שהתקבלו.
- **עדכון המונה אטומי** — באותה טרנזקציה של רישום התמונה, שלא ייווצר פער בקריסה.
- **במחיקת גלריה/תמונה** — המונה יורד באותה טרנזקציה.
- **המכסה מהחבילה** בזמן הבדיקה; דריסת-אדמין גוברת.

## ב.4 התאמה תקופתית (reconciliation)

מונים סוטים (מחיקות שנכשלו, קריסות). עבודת-רקע תקופתית: סוכמת את הגודל האמיתי של
האובייקטים תחת התחילית של כל דייר בדלי, משווה למונה, ומתקנת סטייה. זה גם מגלה
"אובייקטים יתומים" (נמחקו במסד אך נשארו בדלי) לניקוי.

## ב.5 מחזור-חיים ושמירה

| אירוע | מה קורה לבייטים |
|---|---|
| מחיקת גלריה | משוחררים מיד, המונה יורד |
| חריגה ממכסה | חוסם העלאות חדשות; הקיים נשאר נגיש |
| מנוי פג | הגלריות **נסגרות ללקוחות** (unpublish), אך הבייטים **נשמרים** לחלון-חסד |
| סוף חלון-החסד | הבייטים נמחקים מהדלי (חוסך עלות) |

**עקבי עם `LICENSING.md` §2:** אלה תצוגות באחסון *שלך*, לא הגלם של הצלם — אז מדיניות
מחיקה כאן היא החלטת-עלות, לא סיכון לצלם. הגלם שלו על הדיסק שלו, תמיד.

## ב.6 שקיפות לצלם

בפורטל: פס "נוצל X מתוך Y", ופירוט לפי גלריה. שקוף, לא מפתיע.

## ב.7 הכרעות-מוצר בתחום הזה (רק אתה)

# תחום ג' — בידוד דיירים ואבטחת-נתונים

## ג.0 העיקרון

צלם אחד **לא** ייגע בשל אחר — לא בקריאה ולא בכתיבה, בשום תחבולה. הבידוד חי בשתי
חזיתות שחייבות להיות אטומות **שתיהן**: ה-API (הרשאות) והאחסון (מפתחות + כתובות).
מסד אחד ואחסון אחד עם בידוד **לוגי** לפי דייר — סטנדרט SaaS — אבל הבידוד חייב להיות
אכיף בכל נקודה, לא "בדרך כלל".

## ג.1 בידוד ב-API — לפי בעלות (קיים, אומת)

- כל פעולה על משאב נגזרת מ-`user_id` שמגיע **מאסימון-החשבון**, אף פעם לא מפרמטר
  ששלח הלקוח. אי אפשר "לבקש בשם מישהו אחר".
- `_own_gallery`: `user_id != current → 404` (אומת, `galleries.py:47`). כל פעולה
  מוטבעת (קריאה/העלאה/פרסום/בחירות) עוברת דרכו.
- **כלל מחייב:** פונקציית-עזר אחת שתמיד מזריקה `user_id` לשאילתה, שלעולם לא יישכח
  מסנן בקצה חדש.
- **404 אחיד**, לא 403 — לא לחשוף אפילו *קיום* של משאב של אחר.

## ג.2 בידוד באחסון — מפתחות לפי דייר

- מבנה-מפתח: `t/{user_public_id}/{gallery_token}/{image_id}_{size}.jpg` — כל דייר
  תחת התחילית שלו. באג בגלריה אחת לא יכול לגעת בנתיב של דייר אחר.
- **סניטציה נגד path-traversal** במפתח (קיים ב-`LocalStorage._path`; חובה גם ב-R2).

## ג.3 הגשת הקבצים ללקוח — החור הנוכחי, והתיקון

היום `serve_asset` **בלי אימות**, מוגן רק ב-token. מקובל לתצוגות-לקוח, אבל לא מספיק לייצור:
- **URL חתומים ופגי-תוקף** (presigned R2 / signed CDN URL) — קישור שדלף פג מעצמו.
- אחרי הזנת קוד-גישה → **סשן-לקוח קצר-מועד** (JWT מוגבל לאותה גלריה) שדרכו ניגשים
  לנכסים ולבחירות; כתובת-נכס גולמית לא ניתנת לשיתוף מחוץ לסשן.
- ה-token באנטרופיה גבוהה (uuid4 = 122 ביט) — לא ניתן לניחוש.

## ג.4 בידוד במסד

- מסד אחד, בידוד ברמת-שורה לפי `user_id`, מפתחות-זרים קיימים.
- **הקשחה עתידית:** Postgres Row-Level Security — מדיניות שאוכפת בידוד גם אם קצה
  חדש שכח מסנן. חגורה-ושלייקס.

## ג.5 גישת-לקוח לגלריה

- gallery שפורסמה בלי קוד = לפי-קישור-בלבד. עם קוד = קישור + קוד.
- **הגבלת-קצב על ניסיונות קוד** — נעילה אחרי N ניסיונות, נגד ניחוש קוד קצר. (חסר — לבנות.)

## ג.6 וקטורי-תקיפה — רשימה ותשובה

| וקטור | תשובה | מצב |
|---|---|---|
| מניית מזהי-גלריה (IDOR) | owner-scope → 404; הלקוח ניגש ב-token לא-נחיש | ✅ קיים |
| ניחוש כתובות-נכס | token סודי + URL חתומים | חלקי → §ג.3 |
| כתיבה לגלריה של אחר | `_own_gallery` חוסם | ✅ קיים |
| path-traversal במפתח | סניטציה | ✅ ב-local, לבנות ב-R2 |
| SQL injection | SQLAlchemy פרמטרי | ✅ קיים |
| גניבת אסימון | שמירה מוצפנת (DPAPI) + תפוגת-JWT קצרה + רענון | לבנות (צד-אפליקציה) |
| brute-force כניסה | bcrypt + הגבלת-קצב | חלקי (bcrypt קיים) |
| brute-force קוד-גלריה | הגבלת-קצב + נעילה | לבנות |

## ג.7 תעבורה וסודות

- **TLS בכל מקום** בייצור + HSTS. בפיתוח localhost.
- סודות (`SECRET_KEY`, מפתח Ed25519 פרטי, מפתחות R2) בסביבת-שרת, **לא בריפו** (קיים: gitignored).
- **מפתח Ed25519:** גיבוי מחוץ-לפס; רוטציה עתידית עם `key-id` בפתק, כדי להחליף מפתח
  בלי לפסול את כל הפתקים בשטח.

## ג.8 ביקורת והגבלות (לבנות)

- **הגבלת-קצב** per-IP ו-per-account על כניסה, הרשמה, קוד-גלריה.
- **יומן-ביקורת** לפעולות רגישות: כניסה, הפעלה, ביטול, הענקות-אדמין.
- ולידציית-קלט מלאה (pydantic — חלקי היום).

## ג.9 מצב מול נדרש (הכנה לבנייה)

| רכיב | מצב |
|---|---|
| בידוד-API לפי בעלות | ✅ קיים ואומת |
| מפתחות-אחסון לפי דייר | חלקי — לסדר מבנה-מפתח + R2 |
| URL חתומים + סשן-לקוח | ❌ לבנות |
| הגבלת-קצב (כניסה + קוד-גלריה) | ❌ לבנות |
| יומן-ביקורת | ❌ לבנות |
| TLS/HSTS + רוטציית-מפתח | ❌ שלב פריסה |
