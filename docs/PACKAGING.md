# אריזה, הפצה ועדכון — מקור האמת של FrameOps

> המסמך הזה מיועד למתכנת האחרון שנוגע במוצר לפני מסירה. קוראים אותו מתחילתו
> ועד סופו **לפני כל אריזה**, ומוסיפים שורה ליומן שבסופו אחרי כל ניסיון — גם
> ניסיון שנכשל. אין להסיק ש־`release/` מכיל את הקוד הנוכחי רק מפני שיש בו EXE.

עודכן לאחרונה: **24.09.2026**

---

## 1. מה נחשב “מוכן למסירה”

אריזה, פרסום ומסירה הם שלושה דברים שונים:

1. **אריזה** — יצירת מתקין מקומי בתיקיית `release/`.
2. **פרסום** — העלאת המתקין, ה־blockmap וה־`latest.yml` אל `/updates/` בשרת.
3. **מסירה** — שליחת המתקין ללקוח או מתן קישור ההורדה.

קובץ EXE שקיים בדיסק אינו הוכחה שהוא נבדק, פורסם או מתאים לקוד הנוכחי.

ללקוח שולחים **רק את קובץ ההתקנה** (`FrameOps-Setup-<version>.exe`) או קישור
ההורדה הקבוע. לא שולחים את כל תיקיית `release`, לא את `win-unpacked`, לא
`latest.yml`, לא blockmap, לא מפתחות ולא קובצי הגדרה.

## 2. החלטות מוצר שאסור לאריזה לשבור

- תקופת הניסיון היא **30 יום מההפעלה הראשונה במחשב**, לא מההרשמה ולא מתאריך
  האריזה. החלפת חשבון אינה מתחילה ניסיון חדש באותו מחשב.
- אחרי פקיעה התוכנה ננעלת. עבודה לא־מקוונת מותרת רק לפי הפתק החתום והחלון
  שהשרת הנפיק.
- המפתח הפרטי של הרישיונות נשאר **רק בשרת**. למתקין נכנס המפתח הציבורי בלבד.
- כתובת השרת הראשונה מגיעה עם המתקין, ולאחר ההתקנה נשמרת אצל המשתמש תחת
  `LOCALAPPDATA\TEZA\server.json`. מעבר דומיין נעשה במנגנון ההעברה המתועד,
  לא בהחלפה שקטה של כתובת בבנייה חדשה בלבד.
- עדכון אינו מותקן באמצע עבודה. הוא יורד ברקע ומותקן בסגירת התוכנה או לאחר
  אישור מפורש של המשתמש.
- הפס העליון של Windows נשאר דק ונפרד מהממשק. שום כפתור של התוכנה, חלון קופץ
  או מסך מלא אינו רשאי להיכנס מתחת למזער/הגדל/סגור.
- התמונות המקוריות נשארות במחשב הצלם. לגלריית הלקוח עולות תצוגות בלבד.
- אזור המנהל, האתר והגלריה רצים בשרת; כלי העריכה והמנוע נארזים בתוכנה.

## 3. מצב הייצור הנוכחי

### תוכנת Windows

- גרסת המקור ב־`package.json`: **0.2.0**.
- כתובת הייצור: `https://www.yosefautomations.com` (דומיין זמני).
- `release-config/license.json` קיים ומצביע לכתובת הזו.
- `release-config/license-public.pem` קיים.
- ב־24.09.2026 `npm run license:preflight` עבר מול שרת הייצור: השרת חי,
  מזוהה כ־TEZA production והמפתח הציבורי המקומי תואם לשרת.
- קיימת חבילת `TEZA-Setup-0.2.0.exe` שנבנתה ב־24.09 בשעה 01:30, אבל היא
  **ישנה ביחס לקוד הנוכחי**: תיקון חפיפת פס החלון נעשה אחריה, והגדרת המוצר
  הנוכחית כבר יוצרת `FrameOps-Setup-*`. אין למסור אותה כחבילה הסופית.
- האריזה הבאה חייבת לקבל מספר גרסה חדש — לפחות **0.2.1**. בנייה חוזרת של
  `0.2.0` לא תגיע כלקוח שכבר מחזיק `0.2.0`, כי מנגנון העדכון אינו מתקין אותה
  גרסה שוב.

### שרת

- Docker אינו משמש בפריסה בפועל. השרת מארח עוד אתרים, ולכן אין לתת ל־Caddy
  לתפוס את הפורטים 80/443.
- הפריסה בפועל היא שירות FastAPI מאחורי **nginx** הקיים.
- nginx חייב לשמר את ההתנהגות הבאה:
  - `/api/*` עובר לבקאנד **אחרי הסרת `/api`**, כמו `handle_path` ב־Caddy.
  - `/auth/*`, `/licenses/*` ו־`/health` עוברים ישירות לבקאנד.
  - `/updates/` מוגש כתיקייה סטטית.
  - `latest.yml` נשלח עם `no-cache`.
  - קובצי המתקין וה־blockmap תומכים `Accept-Ranges` ואין לדחוס אותם בדרך.
- הנתונים בפריסה הנוכחית נמצאים תחת `projects/managphoto/data/`, ולא תחת
  `/data`. זה תקין לפריסה המקומית הזו כל עוד משתני הסביבה של השירות מצביעים
  לשם והספרייה מגובה.
- `scripts/validate-production.py` באתר נכתב לפריסת Docker המצפה ל־`/data`;
  כישלון שלו על השרת הנוכחי אינו לבדו הוכחה שהשירות שבור. יש לאמת את משתני
  הסביבה והנתיבים של השירות האמיתי.
- `PAYMENT_PROVIDER=stub`: ניסיון ורישוי עובדים; חיוב אמיתי עדיין אינו מחובר.
- Google OAuth אינו פעיל עד להגדרת `GOOGLE_CLIENT_ID` ו־
  `GOOGLE_CLIENT_SECRET`.

## 4. המפתחות — הנכס שאסור לאבד

השרת חותם פתקי רישיון ב־Ed25519:

- פרטי: `ManagPhoto/server/keys/license_priv.pem` — נשאר בשרת בלבד.
- ציבורי: `ManagPhoto/server/keys/license_pub.pem` — העתק שלו נכנס אל
  `photo/release-config/license-public.pem`.

המפתחות נוצרים בעת השימוש הראשון שדורש אותם — גם קריאה אל
`/licenses/public-key` יכולה ליצור אותם, לא רק הנפקת הרישיון הראשון.

### כלל גיבוי

לפני שהלקוח הראשון מקבל חבילה:

1. לוודא שהמפתח הפרטי קיים בשרת.
2. ליצור לו גיבוי מוצפן במקום נפרד מה־VPS.
3. לבדוק שניתן לקרוא את הגיבוי ושגודלו אינו אפס.
4. לתעד ביומן שלמטה שנוצר גיבוי — **לא** לתעד את תוכן המפתח או להעתיק אותו
   ל־Git, למחשב הלקוח, ל־release או לצ'אט.

אובדן המפתח הפרטי פירושו שהשרת לא יוכל לחדש רישיונות שכבר נמסרו. יצירת זוג
חדש אינה “תיקון”; מתקינים קיימים דוחים חתימות מהמפתח החדש.

## 5. קבצים מקומיים שאינם נכנסים ל־Git

| קובץ | תפקיד |
|---|---|
| `release-config/license.json` | כתובת שרת הרישוי הראשונית |
| `release-config/license-public.pem` | המפתח הציבורי שהמנוע והמעטפת מאמתים |
| `release-config/deploy.json` | SSH ונתיב `/updates/` לצורך העלאה |

`deploy.json` נבנה לפי `release-config/deploy.example.json`. הוא חייב להצביע
לנתיב ה־updates של פריסת nginx האמיתית. אין להעלות אף אחד מהקבצים הסודיים או
הפרטיים ל־Git.

## 6. סדר האריזה המחייב

### שלב א — קיבוע מצב המקור

1. לוודא שנמצאים בענף `main`. אסור ליצור או לעבור לענף אחר.
2. להריץ `git status -sb` ולרשום ביומן אילו שינויים נכללים בחבילה.
3. לקמט את יחידת העבודה המיועדת למסירה. אין לארוז בטעות קוד לא שמור בלי
   לתעד במפורש שזה מה שנעשה.
4. להעלות את מספר הגרסה ב־`package.json`. הוא חייב להיות גבוה מכל גרסה שכבר
   נבנתה או פורסמה.

### שלב ב — שרת ורישוי

1. לבדוק `https://<domain>/health`.
2. לבדוק שהמפתח הפרטי קיים ומגובה.
3. לוודא ש־`release-config/license.json` מצביע לדומיין הנכון.
4. להעתיק/לייצא מהשרת את **המפתח הציבורי בלבד** אל
   `release-config/license-public.pem`.
5. להריץ:

```powershell
npm run license:pin
npm run license:preflight
```

ה־preflight חייב לעבור מול השרת הציבורי. אין לעקוף אותו ואין לארוז במצב dev.

### שלב ג — בדיקות מקור

```powershell
npm test
npm run build
```

אם השתנו קובצי מנוע, דרישות Python, מנגנון רישוי או קיבוע המפתח — לבנות את
המנוע מחדש. `package:win:full` עושה זאת, אך יש לוודא שהסביבה והדרישות מעודכנות.

### שלב ד — בניית חבילת Windows

```powershell
npm run package:win:full
```

הפקודה:

1. מקבעת את טביעת המפתח הציבורי במנוע.
2. בונה את `teza-engine.exe` באמצעות PyInstaller.
3. מריצה preflight נגד שרת הייצור.
4. בונה את ממשק React.
5. יוצרת מתקין NSIS, blockmap ו־`latest.yml` בתיקיית `release/`.

אין להשתמש בקבצים ישנים שנשארו ב־`release/`. מקור האמת הוא שם הקובץ המופיע
בתוך `release/latest.yml`, והוא חייב להתאים לגרסה שב־`package.json` ולשעת
הבנייה הנוכחית.

### שלב ה — בדיקת המתקין לפני פרסום

להתקין על מחשב/משתמש Windows נקי ולבדוק לפחות:

- התקנה, הפעלה וסגירה ללא חלון שחור או תלות בשרת פיתוח.
- הרשמה וכניסה, והתחלת 30 הימים רק בהפעלה הראשונה.
- ניסיון להתחבר מחשבון שני באותו מחשב אינו מאפס את התקופה.
- פתק חתום עובד ללא אינטרנט בתוך החלון המותר.
- החזרת שעון לאחור אינה מאריכה שימוש.
- לאחר פקיעה התוכנה ננעלת.
- הפס האפור העליון דק; בכל מסך מלא ובכל חלון קופץ הכפתורים של התוכנה נשארים
  מתחת למזער/הגדל/סגור וניתנים ללחיצה.
- פתיחת פרויקט קיים, ייבוא, סינון, עריכה, ייצוא ואלבום.
- בגלגלת מעל תמונת העריכה מתבצע זום; גרירה מזיזה את התמונה.
- במסך העריכה מוצגת כברירת מחדל בחירת הלקוח מחולקת לפי המקבצים המקוריים;
  התמונות שלא נבחרו מוסתרות ויש פעולה מפורשת להצגתן.
- שליחה ללקוח יוצרת גם שם משתמש/סיסמה וגם קישור תצוגה לצלם, כדי שיוכל לראות
  בדיוק מה הלקוח רואה.
- הגלריה הציבורית נפתחת מהקישור, מציגה תצוגות בלבד ושומרת בחירות והערות.
- הורדת אלבום: זו בעיה שדווחה בעבר ונשמרה להמשך; לפני מסירה שטוענת שהיכולת
  קיימת חייבים לבדוק אותה בפועל.

### שלב ו — פרסום עדכון

אחרי שהוגדר `release-config/deploy.json`:

```powershell
npm run release:upload
```

או לבנייה והעלאה ברצף:

```powershell
npm run release
```

סקריפט ההעלאה שולח קודם את המתקין וה־blockmap ורק בסוף את `latest.yml` בשם
זמני ואז מחליף אותו אטומית. אסור להעלות `latest.yml` ראשון — לקוח עלול לראות
גרסה שקובץ ההתקנה שלה עדיין לא הושלם.

לאחר ההעלאה בודקים מבחוץ:

- `/updates/latest.yml` מחזיר את הגרסה החדשה ו־`Cache-Control` מונע מטמון.
- `/updates/<installer>` מחזיר את הגודל הנכון ותומך בבקשת Range.
- הקישור `/updates/FrameOps-Setup.exe` מפנה למתקין האחרון.
- עותק מותקן של הגרסה הקודמת מוצא את העדכון, מוריד אותו ומציע הפעלה מחדש.

**לא מוחקים גרסאות ו־blockmaps ישנים מהשרת.** עדכון חלקי עשוי להזדקק ל־
blockmap הקודם. חזרה לאחור נעשית על ידי פרסום הקוד הישן תחת מספר גרסה חדש;
האפליקציה אינה מבצעת downgrade.

## 7. מה עבד ומה לא

### עבד

- Electron + NSIS יצרו מתקינים מלאים בגודל כ־1.76GB.
- מנוע PyInstaller נארז ורץ לצד Electron.
- preflight מזהה שרת production ומשווה את מפתח Ed25519 המקומי לזה שבשרת.
- nginx יכול לשרת את האתר, ה־API והרישוי לצד אתרים נוספים בלי Docker ובלי
  להשתלט על 80/443.
- `latest.yml` + blockmap הם המבנה הנכון ל־electron-updater.
- תיקון גבול `#root` ב־`src/design/desktop.css` מונע ממסכים קבועים לעלות מתחת
  לכפתורי החלון.

### לא עבד / אסור לחזור עליו

- חבילת `0.1.0` מ־18.09 נבנתה לפני מערכת הרישוי החדשה. אין למסור אותה.
- עצם קיומה של חבילת `0.2.0` אינו אומר שהיא עדכנית; היא קדמה לתיקוני מקור
  מאוחרים יותר.
- פריסת Docker/Caddy אינה מתאימה ל־VPS הנוכחי משום שהפורטים 80/443 כבר
  משמשים את nginx ואתרים אחרים.
- `validate-production.py` של אתר ה־Docker מניח `/data`; אין להשתמש בכישלון
  הנתיב הזה כאבחנה לפריסת nginx בלי לבדוק את שירות הייצור האמיתי.
- בנייה מחדש באותו מספר גרסה אינה עדכון. תמיד מעלים גרסה.
- אסור ליצור זוג מפתחות חדש לאחר מסירה, ואסור לארוז לפני גיבוי המפתח הפרטי.
- אסור לשלוח ללקוח את כל תיקיית `release`.

## 8. מעבר דומיין בעתיד

הדומיין הנוכחי זמני. מעבר מסודר דורש:

1. להפעיל את השרת החדש עם **אותו מפתח פרטי** ומסד הנתונים הרלוונטי.
2. לוודא שהמפתח הציבורי בחדש זהה לזה שהותקן אצל הלקוחות.
3. לפרסם בשרת הישן `updates/server.json` באמצעות:

```powershell
npm run server:move -- https://הדומיין-החדש
```

4. להשאיר את הדומיין הישן פעיל כמה חודשים כדי שגם מחשב שלא נפתח זמן רב יקבל
   את ההודעה.
5. לעדכן את `release-config/license.json` לפני בניית מתקינים חדשים.

לעולם לא מעבירים דומיין באמצעות יצירת מפתח חדש.
