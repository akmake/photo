# ARCHITECTURE — עורך התמונות (שם זמני: "סטודיו")

> מסמך זה הוא **מקור-האמת**. כל קוד שנכתב חייב להתאים לו. אם משהו נבנה בסתירה למסמך — או המסמך מתעדכן קודם, או הקוד לא נכנס. המסמך מתוחזק תוך כדי, לא בדיעבד.

---

## 1. מה אנחנו בונים

כלי פוסט-פרודקשן **מקומי** לצלמות (נישה: מגזר חרדי, עברית).
זרימה: מייבאים תיקייה → בונים **מתכון עריכה** (כלים גלובליים + כלי AI) על תמונת ייחוס → מחילים על כל הסשן → מייצאים. הכל מקומי, פרטי, שום תמונה לא עוזבת את המחשב.

חזון-על (North Star): "כל מה שצלמת צריכה, במקום אחד". **הטריז שבונים עכשיו: העורך.** מעצבים אותו כך שיגדל לפלטפורמה — לא בונים את הכל בבת אחת.

---

## 2. עקרונות-על (לא ניתנים למשא ומתן)

1. **Pipeline אחד, מקור-אמת אחד.** המנוע (Python) מריץ את *כל* שרשרת העריכה. `preview == export` תמיד.
2. **כל כלי הוא אזרח אחיד.** גלובלי (חשיפה) או AI (החלקת עור) — אותו `Tool` interface, אותו pipeline, אותו מתכון. אין "האק".
3. **עריכה לא-הרסנית.** מתכון = stack מסודר של שכבות. המקור אף פעם לא משתנה.
4. **עלות-החישוב על חשבון המשתמש, לא על חשבון העסק.** ברירת מחדל: עיבוד על מחשב המשתמש. **הרציונל הוא כלכלי, לא אידאולוגיית-פרטיות:** אם העסק צריך לארח שרתים שירוצו את העיבוד הכבד (AI) עבור כל צלמת ואצווה, זו עלות-תשתית שמצטברת לאינסוף. **אין פסול באינטרנט עצמו** — קריאת-רשת שהמשתמש עצמו נושא בעלותה (למשל מפתח-API אישי לשירות AI חיצוני, ששולם ישירות לספק ולא דרך העסק) עומדת באותו עיקרון בדיוק כמו הרצה מקומית, כי בשני המקרים העלות לא נופלת על העסק. מה שכן אסור: העסק מארח/ממן חישוב-כבד מרוכז בשביל המשתמשים. אין שרת-ענן בבעלות-העסק ל-v1.
5. **בונים כדי לשמור.** בלי קיצורי-דרך שקטים. פרוטוטייפ זריק — רק בהכרזה מפורשת ובאישור.
6. **רישוי מסחרי בלבד.** מודלי קוד-פתוח: MIT / Apache / BSD בלבד. אסור לא-מסחרי (CodeFormer, BRIA RMBG).

```
│  · מדליק ומנהל את המנוע כ-sidecar                             │

│                                                              │
│   ┌────────────────────────┐     ┌───────────────────────┐   │
│   │  Renderer (React + TS) │◄───►│  Engine (Python)      │   │
│   │  · UI, ערימת המתכון    │ IPC │  · מקור-האמת לעיבוד   │   │
│   │  · תצוגה מקדימה מהירה   │/HTTP│  · RAW, גלובלי, AI    │   │
│   └────────────────────────┘     └───────────────────────┘   │
└─────────────────────────────────────────────────────────────┘

```

- **Renderer** — כל ה-UX ותצוגה מקדימה *מהירה* (JS/WebGL על proxy מוקטן) לחוויית סליידר מיידית.
- **Engine** — מקור-האמת: פענוח RAW, הכלים הגלובליים ה"אמיתיים", וכל כלי ה-AI. הוא שמרנדר את הייצוא הסופי.

> **הבהרה:** "כלום לא יוצא מהמכונה" למעלה מתאר את מה שבנוי היום (v1) — לא איסור עתידי על כל קריאת-רשת. ראו עיקרון #4 לעיל: קריאה לשירות חיצוני שהמשתמש עצמו משלם עליה ישירות (לא דרך העסק) לא סותרת את העיקרון, כי העיקרון הוא כלכלי (מי נושא בעלות-החישוב), לא איסור-פרטיות גורף.

## 4. מודל הדומיין (Core data model)

```ts
type ToolKind = 'global' | 'ai';
type BatchPolicy = 'absolute' | 'adaptive'; // איך הכלי מתנהג באצווה

interface ToolParamSpec {
  id: string; label: string;
  min: number; max: number; step: number; default: number;
}

// מופע של כלי בתוך מתכון: איזה כלי + ההגדרות שהצלמת בחרה
interface ToolInstance {
  toolId: string;
  params: Record<string, number>;
  enabled: boolean;
}

// המתכון = ערימה מסודרת של כלים. זה הלב.
interface Recipe {
  tools: ToolInstance[];
}

// סגנון שמור בשם ("לוק ים", "TEZA Warm") — שכבה 3
interface Style {
  id: string; name: string; recipe: Recipe;
}

interface Photo {
  id: string;
  path: string;        // נתיב מקומי — המנוע קורא ישר מהדיסק
  name: string;
  recipe: Recipe;      // המתכון שהוחל על התמונה הזו
}

interface Session {   // "סשן" = תיקייה/גלריה של עבודה
  id: string; name: string;
  photos: Photo[];
}
```

## 5. חוזה הכלי (ה-interface האחיד)

**זה המנגנון שמונע "האקים".** כל כלי — גלובלי או AI — מממש את אותו הדבר:

```ts
interface ToolDef {
  id: string;
  label: string;              // עברית
  kind: ToolKind;
  category: ToolCategory;     // קובע סדר ב-pipeline
  params: ToolParamSpec[];
  batchPolicy: BatchPolicy;
}
```

צד-מנוע, כל כלי מספק:
```python
def analyze(image, ctx) -> dict:   # אופציונלי: הצעת ערכים / חישוב מסכה מראש
    ...
def apply(image, params, ctx) -> image:   # ההחלה עצמה
    ...
```

**סדר ה-pipeline** (לפי `category`, קבוע וצפוי):
```
raw-develop → local-ai (skin, eyes, face) → tone/color (global)
            → scene (background blur, sky) → artistic
```
### MaskProvider — הליבה של כל כלי ה-AI

**כל כלי AI במוצר הוא (מסכה + פעולה).** לכן יש מקום *אחד* שעונה "איפה נמצא X בתמונה" — `engine/masks.py`:

```python
get_mask(rgb, kind) -> float32 mask (H,W) in 0..1
# kinds: subject | hair | face-skin | body-skin | eyes | cheeks
```

מודלים: **MediaPipe** (Apache 2.0) — `selfie_multiclass_256x256` לפילוח, `face_landmarker` ל-478 נקודות. רצים מקומית, יורדים דרך `engine/setup_models.py` (לא ב-git).

**המשמעות:** כלי AI חדש = לבחור kind + לכתוב פעולת פיקסלים. **לא לחבר מודל חדש בכל פעם.**

### עומק (`engine/depth.py`) — MiDaS small (MIT) דרך onnxruntime

> **כלל:** "לחתוך את הנושא ולטשטש אחיד את כל מה שמאחור" מייצר **אפקט מדבקה** — כי בעדשה אמיתית הטשטוש **גדל עם המרחק**. לכן טשטוש הרקע מרכיב מספר רמות טשטוש לפי `|depth − subject_plane|`: הקרקע לרגלי המצולם נשארת חדה, הרקע הרחוק נמס, וגם החזית הקרובה מתרככת — כמו עומק שדה אמיתי. **בוקה** מתקבל מקרנל **עגול** + פריחת היילייטים, לא מגאוסיאן.
>
> *מגבלת זיכרון ידועה:* קומפוזיציית הרמות מחושבת על התמונה כולה — לייצוא ברזולוציה מלאה נצטרך לעבוד באריחים (tiles).

> **כלל מוצר — EXIF orientation חובה:** מצלמות שומרות צילום פורטרט כ**לרוחב + תג סיבוב**. דפדפנים מיישמים את התג, PIL **לא**. בלי `ImageOps.exif_transpose` בכל טעינה: MediaPipe מנתח תמונה שוכבת ולא מוצא פנים, והתוצאה חוזרת **מסובבת ב-90°** ביחס לתצוגה. מיושם ב-`common.load_image` / `b64_to_image`.

> **כלל מוצר — זיהוי פנים דו-שלבי:** הגלאי המובנה של MediaPipe הוא **short-range** — הוא מצפה שהפנים ימלאו חלק ניכר מהפריים, ומחזיר **ריק בשקט** לפנים שהן 10% מקובץ 3648px. זה השבית בשקט את *כל* מסכות ה-landmarks (עיניים, לחיים, תווים). הפתרון ב-`_face_landmarks`: מנסים על הפריים המלא, ואם ריק — **מאתרים פנים דרך הפילוח** (עובד בכל קנה מידה) ומריצים landmarks על **crop**, ממפים בחזרה. *(אותה תבנית שהצילה את החיתוך.)*

> **כלל מוצר — מסכת תווים מוגנים (`face-features`):** עיניים + **גבות** + שפתיים + נחיריים **אף פעם** לא עוברים ריטוש. בלי זה מחיקת "כתמים כהים" מוחקת לילדה את הגבות. כל כלי פנים חייב להחריג את המסכה הזו.

### מודל העור (`engine/skinmodel.py`) — הליבה של ריטוש הפנים

**היפוך התפיסה:** במקום לתאר *איך נראה פגם* (רשימה שרירותית שלעולם לא נגמרת — כהה, אדום, בהיר, צהוב…), בונים מודל של **מהו העור של האדם הזה**, וכל מה שהמודל לא מסביר הוא פגם — **בכל כיוון**.

**הפרדת תדרים היא מה שמציל את הסומק:**

| | קנה מידה | תדר | מה עושים |
|---|---|---|---|
| סומק, גוון אישי, צל רך | ענק | **נמוך** | `low` — **לא נגיש לכלי כלל** |
| פגם | קטן ומוגדר | **בינוני** | `mid` — כאן פועלים |
| נקבוביות, רעש | זעיר | **גבוה** | `high` — נשמר |

המודל הוא **משטח חלק** (normalized convolution על מסכת העור בלבד), ולכן הוא **מתעקל מעצמו** להיות ורוד בלחיים ובהיר במצח — **הסומק נבלע בתוכו**. זו **ערובה מבנית**: הכלי מרכיב את `low` ללא שינוי, ולכן *מתמטית* אינו יכול לנטרל צבע טבעי.

> **שקלול צבע > בהירות (`W_L=0.25, W_A=1.0, W_B=0.7`):** קמט הוא **גיאומטריה** — משנה בהירות, שומר צבע. פגם הוא **פיגמנט** — משנה צבע. בשקלול שווה הגלאי סימן את קו החיוך, קמט העפעף וקו הסנטר — וריטוש שלהם משטח את הפנים. הנמכת משקל `L` הופכת אותו כמעט עיוור למבנה ורגיש לחלוטין לסימנים. *(במדידה: 4245 → 1319 פיקסלים מתוקנים, וקו החיוך יצא מהתמונה.)*

> **ריפוי במקום מילוי:** `cv2.inpaint` *ממלא חור* מהשוליים פנימה → כתם שטוח חסר מרקם ("פלסתר"). במקומו: `low + mid*(1-conf) + high*(1-conf*0.3)` — הצבע נשמר, הפגם מוסר, **המרקם נשאר**.

> **מפת ביטחון רציפה, לא מסכה בינארית:** מסכה בינארית יוצרת קצה חד. הביטחון נגזר מהמרחק הסטטיסטי דרך smoothstep, והתיקון פרופורציונלי לו.

**רשת ביטחון:** רכיב גדול מ-16% מרוחב הפנים לעולם אינו "פגם" — הוא אופי עור שהמודל לא הצליח לבלוע. נדחה.

**`engine/test_blush.py` — assertion אוטומטי:** מודד את צבע תפוחי הלחיים לפני/אחרי בעוצמה מקסימלית ונכשל אם הוא זז מעל 0.6 יחידות Lab. *(נמדד: dL=0.004.)* **להריץ אחרי כל שינוי בגלאי.**

> **כלל מוצר — כתם הוא סטיית *צבע*, לא רק בהירות:** גלאי שבודק רק "כהה יותר" (לומיננס) **עיוור לכל סימן אדום** — וזה רוב הסימנים על פני ילד (גירוי, שריטה, שאריות אוכל). הגלאי עובד ב-**Lab**: סטייה ב-`L` (כהה) *או* ב-`a` (אדום), עם **סף אדפטיבי** לפי סטיית התקן העמידה של העור באותה תמונה — כך הכלי מתנהג זהה על עור נקי בסטודיו ועל עור גרגירי בחוץ.

> **כלל מוצר — שערי צורה חלים רק על כתמים כהים:** שערה היא חומה-כהה ומוארכת; סימן גירוי הוא **אדום** ויכול להיות מוארך גם הוא. להחיל את אותו שער "לא מוארך" על שניהם = לדחות סימנים אדומים אמיתיים. לכן: **כהה → שערי צורה מחמירים** (הגנה מפני שיער); **אדום → שערים מרופפים** (שיער אינו אדום).

> **כלל מוצר — מרווח הגנה לפי סוג התו:** לתווים עם שיער (עיניים, גבות) נדרש מרווח נדיב — ריס או שערת גבה יושבים *מחוץ* לטבעת ה-landmarks. לשפתיים ולאף **אסור** מרווח נדיב: הוא חוסם ריפוי של סימנים *לצד* הפה, שם בדיוק יושבים סימני האוכל/גירוי של ילד.

> **כלל מוצר — כתם מול שערה:** גלאי "כתם כהה קטן" תופס גם שערות פוני/תינוק. שלוש הגנות: החרגת מסכת שיער מורחבת · **פתיחה מורפולוגית** (קו דק נעלם, כתם עגול שורד) · שערי צורה (מוארכות/דלילות נדחות). על תמונת מבחן: 133 → **9** כתמים.

> **כלל מוצר — סף רזולוציה לריטוש פנים:** כלי פנים (ניקיון עור, החלקה, עיניים, סומק) **מסרבים לפעול** כשרוחב הפנים קטן מ-~180px (ניקיון) / ~120px (החלקה), ומחזירים `faceTooSmall`. הסיבה: בפנים של 70px, פצעון ונחיר הם באותו גודל — "ניקוי" מוחק תווי פנים אמיתיים. **עדיף לסרב מאשר לייצר בוץ.** ריטוש פנים אמיתי דורש פנים של 800–1500px, כלומר קובץ מקורי מהמצלמה.

> **לקח מהשטח:** `subject` אינו "כל מה שאינו רקע" — כביסה תלויה מסווגת כ"בגדים" ונכנסה בטעות. התיקון: שומרים רק רכיבים קשירים שמכילים **אדם אמיתי** (עור/שיער).

### פירוק ריטוש העור — ארבעה שלבים, פסק דין לכל אחד

אחרי שבעה ניסיונות שנכשלו כמכלול, פורק הצינור לרכיבים שנבדקים **בנפרד**. זה מה שאיתר סוף-סוף את נקודת הכשל האמיתית — קודם לכן נשפטה רק התמונה הסופית, ולכן כל סיבוב היה ניחוש.

| # | שלב | מה הוא עושה | פסק דין (נמדד) |
|---|---|---|---|
| 0 | **מסכות** | פנים · עור · שיער · **אנטומיה** | 🔴 **מסכת האנטומיה גסה מדי** |
| 1 | **מודל עור** | novelty — מה המודל לא מסביר | 🟢 עובד |
| 2 | **החלטה** | מ-novelty למסכת תיקון | 🔴 **שבור — צורת המסכה** |
| 3 | **ריפוי** | בונה מחדש את מה שמתחת למסכה | 🟢 עובד |
| 4 | שיקול דעת | שומה מול פצעון | ⚪ נדחה בכוונה |

**ראיות:** שלב 1 סימן כתם גדול **בדיוק** על השריטה — הוא ראה אותה. שלב 3 ניקה אותה לגמרי כשקיבל מסכה ידנית. בין שני שלבים עובדים, התוצאה מתפרקת ב-2.

> **הכשל המרכזי — נגע הוא *אזור*, אבל ההחלטה היא *פר-פיקסל*.** סף על מפת ביטחון מייצר **רסיסים מנוקבים**, לא גוש רציף. מדוד על אותה שריטה: מסכה ידנית = **גוש אחד, 631px** → נוקתה. מסכה אוטומטית = **100 רסיסים, 3404px** → לא זזה.
>
> וזה קטלני דווקא בגלל שהריפוי עובד: שחזור בונה מחדש מהפיקסלים **שסביב** המסכה. כשהמסכה מנוקבת, ה"סביבה" שממנה הוא דוגם **היא הנגע עצמו** — הוא משחזר את הכתם מתוך הכתם. זה גם ההסבר המאוחר לתלונה "משאיר את המבנה של הסימן": מעולם לא היה זה כשל של הריפוי.

> **שלב 0 ו"דליפת אנטומיה" הם אותה תקלה, לא שתיים.** גבול השפה, קמט הסנטר, צל הנחיר וקו הלסת סומנו כפגמים — כי `face-features` גסה מדי. זו **אינה** בעיית שיקול דעת אלא הנדסה דטרמיניסטית: ל-`face_landmarker` יש 478 נקודות שנותנות את קווי המתאר האלה במדויק. **חייב להיתקן ראשון** — לא כי הוא יפתור, אלא כי בלעדיו מפת הזיהוי מוצפת קמטים ואי אפשר להבחין בין "פספס לכלוך" לבין "סימן קמט".

> **באג — `patch_frequency` סתר את התיעוד של עצמו.** ה-docstring הבטיח "מעביר רק תדר גבוה של התורם"; הקוד חישב `donor_low + tone_delta + donor_high`, כלומר **השתיל את כל מבנה הטלאי** והמציא קמט שלא היה. הוחלף ב-`inpaint-texture`: הטון מדיפוזיה (שם היא מצוינת — מתפרה לפי התאורה סביב), והתורם תורם **אך ורק** מרקם נקבוביות (מה שדיפוזיה הורסת). מרקם נמדד בתוך התיקון מול הטבעת סביבו: Telea 0.42 · patch-frequency 0.59 *(+ארטיפקט)* · **inpaint-texture 0.68**.

> **באג — שחזור הוא הכל-או-כלום, ואסור למזג אותו בשקיפות חלקית.** מיזוג התוצאה עם המקור לפי ערך הביטחון משאיר **רפאים פרופורציונליים של בדיוק מה ששוחזר**. שחזור מוחל במלואו בתוך המסכה, עם feather צר לתפר בלבד. *(זה שונה מריפוי-תדרים, שתוכנן לביטחון רציף — שתי שיטות, שני חוזים.)*

> **הערובה המבנית לסומק משתנה במצב שחזור.** בריפוי-תדרים `low` הורכב ללא שינוי, ולכן נטרול צבע טבעי היה **בלתי אפשרי מתמטית**. שחזור בונה טון מחדש ולכן אינו נהנה מזה. מה שמחליף את הערובה: **שער הגודל** — משחזרים רק נגעים קטנים דיים שהטבעת המזינה את הדיפוזיה היא אותה חתיכת עור, כך שסומק מקומי משוחזר ולא מוחלק. `test_blush.py` הוא מה שמחזיק את זה כן.

#### מצב נוכחי — צעדים 1 ו-2 בוצעו

**צעד 1 — `face-anatomy` (`masks.py`)** ✅ מסכת הגנה מ-478 נקודות ציון, **מוחזרת כרשימת חלקים בשם** (`anatomy_parts()`) ולא כגוש: עפעפיים · אף · שפתיים · קמט אף-שפה · קמט סנטר · קו מתאר. `cleanup.py` צורך אותה במקום `face-features`.
> **עין+גבה כ-hull אחד** — קמט העפעף חי *ביניהן*, ו-hull נפרד לכל אחת השאיר בדיוק את הקמט שהגלאי סימן.
> **הפסים צרים בכוונה**, ויש assertion שמודד זאת: הסימן ליד הפה מוגן **1.2%** בלבד. פס רחב היה הופך את הסימנים שהכי צריך להסיר לבלתי-נגישים לצמיתות.
> תוצאה: גבול השפה, קמט הסנטר וצל הנחיר נעלמו מהמפה. 3404 → 2384 px. *(עדיין דולף: האוזן, ומעט מתחת לעין.)*

**צעד 2 — `cleanup.decide()` — היסטרזיס** ✅ שני ספים עם תפקידים שונים: **גבוה (0.60) מחליט *האם* זה נגע** (ליבה בטוחה), **נמוך (0.22) מחליט *עד לאן הוא מגיע***. רסיס בלי ליבה נזרק; נגע אמיתי שומר את ההילה שסף בודד חתך. ואז סגירה מורפולוגית + מילוי חורים → כל נגע יוצא **מלא**.

> **באג — השער מדד את האזור *המורחב*.** היסטרזיס הרכיבה את השריטה לנגע אחד, והשער מחק אותה **בדיוק בגלל שהורכבה**. השער נמדד מעתה על ה**ליבה**, לא על ההילה.
>
> **באג — השער מדד תיבה חוסמת.** תיבה מענישה סימן על היותו **ארוך**. נמדד: ליבת השריטה **38×50** מול שער 45 → נדחתה, כששטחה בפועל **396px בלבד**. זו **אותה טעות** ששער-הצורה-נגד-שיער כבר עשה פעם (ראה הכלל למעלה) — **אורך אינו ראיה לחפות**. השער מודד מעתה **שטח + עובי** (`distanceTransform` — העיגול הגדול ביותר שנכנס בסימן): שריטה דקה עוברת, סומק רחב נדחה.

**צעד 3 — הפרדת "מהיכן דוגמים" מ"היכן שופטים" (`skinmodel.build(support=…)`)** ✅ חלקי.

> **הכשל שנמדד — הגלאי בזבז את הביטחון שלו על שולי תווים.** `region` מנכה קמטים, פס מתאר ושוליים שחוקים — נכון לצורך *ריפוי*, אבל הם עדיין דוגמאות מצוינות לעור של האדם הזה. כשדוגמים רק בתוכו, המשטח החלק מוערך **חד-צדדית** לאורך כל גבול, וחד-צדדיות נקראת כסטייה. נמדד: novelty חציוני יורד מונוטונית עם המרחק מהגבול (1.52 ב-0-4px מול 0.60 ב-60px+), וליבות ישבו במרחק חציוני **4.4px** מגבול מול **12px** של עור טיפוסי. לכן סימן בעור פתוח כמעט לא יכול היה להתחרות. התיקון: `support = skin − face-features − hair` (בלי שחיקה, בלי קמטים) לדגימה; `region` נשאר לשיפוט.
>
> **תוצאה — שיפור אמיתי אך חלקי.** 1.52 → **1.18** בטווח 0-4px; מרחק חציוני של ליבה 4.4 → **6.0px**. `test_blush` PASS (dL=0.006). אבל **דפוס הסימון כמעט לא השתנה ויזואלית** — עדיין אוזן, מתחת לעיניים, קמט הנחיר ומסביב לשפתיים. חלק מהמדרון כנראה פיזי (שערות, צללי ריסים, גלישת גבול השפה) ולא ארטיפקט.

**צעד 5 — פירוק ה-hull של עין+גבה לשלושה חלקים לפי מה שהם באמת** ✅

> **הכשל — הגנה שנגע אמיתי אינו יכול לחמוק ממנה אינה זהירות, היא נקודה עיוורת.** המשתמש הצביע על **כתם דלקתי אדום על העפעף העליון החיצוני** (`2210-2250, 2170-2200`). נמדד: **0.0% כשיר, `conf` מקסימלי 0.00** — הצינור מעולם לא שקל אותו. והצבע מרשיע: `dL=+0.4, da=+3.0, db=+4.7` מול הטבעת סביבו — **פיגמנט, לא גיאומטריה**, בדיוק המחלקה ש-`W_A=1.0` נבנה כדי לתפוס.
>
> **שיעור מתודי:** בסבב קודם פסלתי את הפיצול על סמך מדידת "קופסת גבה" — המדד היה לא נכון, הנגע לא היה בו. **מדד שאינו מכיל את המקרה שבגללו מודדים אינו ראיה.**

> **hull לדברים שהם אזורים, רצועה לדבר שהוא קו.** ה-hull המאוחד היה נכון בכוונתו — קמט העפעף חי בין העין לגבה — אבל hull הנמתח מקו הריסים לגבה הוא **קמור**, ולכן מתנפח מעבר לזווית העין החיצונית ובולע את העפעף. זו **אותה טעות** שמסכת השפתיים כבר עשתה ("hull שמן חסם ריפוי של סימנים לצד הפה"). הפירוק: `eye-l/r` (hull + 3.0% לריסים) · `brow-l/r` (hull + 1.2%) · `eyelid-crease-l/r` — **רצועה** לאורך קו הריסים, מורמת 3.5% ובעובי 5%.
>
> כויל במדידה: הרמה 3.0%/עובי 4.0% משחרר יותר אבל **מדליף 19px לקמט** — נדחה. 3.5%/5.0% שומר את הקמט על **1px, זהה ל-hull המאוחד**, ופותח את העפעף.

> **כלל עבודה — לבקר כל נגע בנפרד, לפני/אחרי.** עד לנקודה זו נמדד תמיד *איפה* הכלי נוגע, אף פעם לא **האם הוא צודק**; לא היה לפרויקט מספר של חיוביים-כוזבים. גיליון מגע של כל הנגעים בזום (לפני|אחרי, עם קו המסכה) חשף מיד ששני שלישים מהעבודה הולכים למקומות שגויים. זו הבדיקה שהייתה חסרה.

> **באג — `face-skin` אינו פנים.** הפילוח מחזיר גם את **האוזן, הצוואר וגלישת הלסת**. נמדד: **28% מכל פיקסל שרופא נחת שם**, על 5.6% מהשטח הכשיר — ייצוג-יתר פי 5. האוזן היא גוש רכסים וצללים ששום מודל עור לא יכול להסביר. התיקון: `region` מוגבל לתוך `face-oval` (מתאר הפנים ממולא). **`support` בכוונה אינו מוגבל** — חיתוך הדגימה באותו קו היה מחזיר בדיוק את הטיית השכנות החד-צדדית.

> **כלל עבודה — כל שלב מוציא תוצר בדיקה משלו.** מסכת האזור · מפת ה-novelty · מסכת ההחלטה · מבחן הריפוי על מסכה ידנית. כך רואים **איזה שלב זז ואיזה נשבר**, במקום לשפוט את התמונה הסופית ולנחש. היעדר הכלל הזה עלה שישה סיבובים.

> **כלל עבודה — לא שופטים ריטוש לפי חיתוך נבחר.** חיתוך של 40px בזום 11x הוא בחירה נוחה, לא ראיה. כל טענה על ריטוש מוצגת על **כל הפנים**, בגודל שאפשר לשפוט, לצד **מפת מה שסומן** — אחרת "עובד" ו"לא נגע בכלום" נראים זהים.

> **החלטה:** ריטוש-AI רץ *לפני* הגראפ הגלובלי. נימוק כפול: (א) איכות — מריטשים על דאטה נייטרלי ואז מגריידים מעל; (ב) ביצועים — תוצאת ה-AI מחושבת מהמקור ונשמרת ב-cache, והכלים הגלובליים רצים חי מעליה ב-JS בלי להריץ AI מחדש בכל תזוזת סליידר.

יש **Tool Registry** אחד; ה-UI נבנה דינמית מהרישום. כלי חדש = הוספה לרישום, בלי לגעת בשאר.

## 6. ה-Pipeline (איך מתכון מרונדר)

`render(photo)` = החלה בסדר של כל `recipe.tools` דרך `apply()`.

שני מסלולי רינדור, אבל **מקור-אמת אחד**:
- **תצוגה מקדימה מהירה** (renderer): כלים גלובליים ב-JS/WebGL על proxy מוקטן → משוב סליידר מיידי. תוצאות AI מגיעות מהמנוע ו**נשמרות ב-cache**.
- **רינדור-אמת** (engine): כל השרשרת (גלובלי + AI) ברזולוציה מלאה — לייצוא ולתצוגת AI. זה מבטיח `preview == export`.

**Cache** — פעולות AI יקרות. מאחסנים פלט לפי `(photo, toolInstance.params)` כדי לא לחשב מחדש בכל רינדור.

## 7. חוזה המנוע (Sidecar API)

```
GET  /health                      → { status, tools[] }
GET  /tools                       → רישום הכלים (id, kind, params, category)
POST /tools/{id}/apply            → { imagePath|image, params } → image  (כלי בודד, לתצוגה/cache)
POST /render                      → { imagePath, recipe, size } → image  (רינדור-אמת מלא)
POST /analyze                     → { imagePath } → הצעות (auto-style, מאפיינים שזוהו)
POST /decode                      → { path | image, maxDim } → תצוגת JPEG   (פענוח RAW)
POST /export                      → { photos[], recipe|perPhoto, format, dest }  (עתידי)
```

**החלטת build-to-keep:** תמונות עוברות ב**נתיב-קובץ מקומי**, לא base64. המנוע קורא מהדיסק (מהיר, חובה ל-RAW/תמונות גדולות). *(ה-base64 ב-POC היה קיצור-דרך — מוחלף כאן.)*

## 8. אסטרטגיית תצוגה מקדימה + סיכון הביצועים ⚠️

**הסיכון האמיתי:** להריץ הכל דרך המנוע גם לתצוגה חיה ← עלול להיות איטי (שנייה לכל תזוזת סליידר = חוויה גרועה).

**המיטיגציה (מובנית בארכיטקטורה):**
- כלים גלובליים → תצוגה מקדימה ב-JS/WebGL על proxy, מיידי.
- כלי AI → נחשבים במנוע פעם אחת, נשמרים ב-cache, ומוצגים כשכבה.
- רינדור-אמת מלא רק בייצוא / כשצריך דיוק.

**נמדוד את זמן הרינדור מוקדם (Phase 1), לא נגלה בסוף.** ✅ נמדד: AI ~210–244ms; רינדור גלובלי מוצג ב-UI (`Xms` ליד שם הקובץ).

> **החלטה מוצהרת — כפילות מבוקרת:** הכלים הגלובליים ממומשים ב-**JS** (תצוגה חיה מיידית — דרישת מוצר) ויְמומשו גם ב-**Python** עבור **ייצוא ואצווה** (שם המנוע חייב לרנדר מאות תמונות ברקע). זו כפילות מכוונת ומוגבלת לסט קטן ומוגדר. **מיטיגציה לדריפט: מבחן parity** (תמונת fixture → השוואת פלט JS מול Python בסבולת) — נכנס יחד עם הייצוא ב-Phase 2. זה לא קיצור-דרך שקט; זה תיעוד של הכרעה.

## 9.1 ביצועים — כללים שנלמדו במדידה

הורדנו מ-**32s** ל-**12.6s** לתמונת 20MP. ארבעה כללים, כולם מדידים:

1. **אל תסריאליזו בין כלים.** כל כלי חושף `apply(rgb, params) -> (rgb, meta)`; ה-base64 הוא רק חוזה ה-HTTP. קידוד PNG של 20MP בין כל שני כלים עלה יותר מהכלים עצמם.
2. **מסכות פעם אחת מהמקור.** `masks.set_source()` — הן מתארות *איפה דברים נמצאים*, וריטוש לא מזיז אותם. פלוס cache.
3. **כלי פנים חותכים לאזור הפנים ועובדים ברזולוציה מלאה.** הקטנה כללית פוגעת בזיהוי כתמים (9→3); crop נותן גם מהירות וגם איכות. *(החלקת עור: 4517ms → 245ms.)*
4. **פונקציה סקלרית = טבלת חיפוש.** חשיפה/WB/shoulder/קונטרסט הם פונקציה פר-ערוץ → מחושבים על **256 ערכים** ולא על 60 מיליון. אזורי טונים → LUT על לומיננס. נפילות מרחביות חלקות (וינייטה, נקודת אור) → נבנות מוקטן ומוגדלות.

## 9.2 איכות ייצוא — נמדד, לא משוער

**איכות מסירה היא לא מקום לחסוך בייטים.** נמדד על קובץ מצלמה 20MP (אותה תמונה, בלי כלים):

| הגדרה | גודל | PSNR | סטייה מקס' |
|---|---|---|---|
| q94 4:4:4 | 4.6 MB | 47.5 dB | 15 רמות |
| **q97 4:4:4 (ברירת מחדל)** | 6.6 MB | 51.3 dB | 13 |
| q100 4:4:4 | 12.5 MB | 56.1 dB | 4 |
| TIFF/PNG | 20+ MB | ∞ | 0 |

**ברירת מחדל: JPEG q97, `subsampling=0` (בלי דילול כרומה), progressive, עם פרופיל ICC.** TIFF (LZW) ו-PNG זמינים כמאסטר ללא אובדן.

> **הבהרה חשובה:** קובץ מיוצא *קטן* מהמקור אינו בהכרח עדות לאובדן איכות. רקע מטושטש נדחס כמעט לאפס — במדידה, ירידה מ-6.2MB ל-2.3MB נבעה ברובה מהטשטוש, לא מהדחיסה. תמיד למדוד לפני שמסיקים.

## 10.1 תקן מקצועי לכל כלי (ביקורת איכות)

> **כלל עבודה:** לכל כלי שואלים "האם הוא מבצע את הרעיון **בצורה מקצועית**?" ואם לא — עוצרים ובונים מחדש. המוצר נמדד בפרטים הקטנים.

| כלי | הגישה הנאיבית (נפסלה) | התקן המקצועי שמיושם |
|---|---|---|
| **חיתוך נושא** | מסכה בינארית 256×256 מנופחת → שיער כמו קרטון | `matting.py`: **confidence masks רכות** + **מעבר שני על crop של הנושא** (פי-3–4 רזולוציית קצה) + ליטוש מול התמונה (guided filter) + עקומת הקשחה לליבה |
| **טשטוש רקע** | חיתוך + טשטוש אחיד → אפקט מדבקה | **מפת עומק** (MiDaS) → רדיוס פר-פיקסל לפי `\|depth − subject_plane\|`; קרנל **עגול** + פריחת היילייטים |
| **טון וצבע** | הכפלת ערכי sRGB → הסטות גוון, שריפה חדה | **חשיפה ואיזון-לבן באור לינארי** + **shoulder רך** להיילייטים + עקומת קונטרסט S (לא סקיילינג לינארי) + מסכות טונליות smoothstep |
| **חידוד** | unsharp על RGB → פרנג'ים צבעוניים | על **לומיננס בלבד** + הגבלת delta נגד הילות |
| **תלת מימדיות** | unsharp ברדיוס גדול → הילות | לומיננס + הגבלת delta + וינייטה עם falloff חלק |
| **גלואו** | טשטוש כל התמונה ו-screen → אובך | פריחה **רק מההיילייטים** (smoothstep 0.55–1.0) |
| **ציור שמן** | blur + posterize | **Kuwahara אמיתי** דרך integral images — O(n), הרדיוס לא עולה כלום |
| **נקודת אור** | חיבור אדיטיבי → שטיחה | **screen blend** עם falloff חלק |
| **החלקת עור** | מסכת צבע YCbCr → מרחה חצי תמונה · ואז bilateral → מוחק נקבוביות | **frequency separation**: מחליקים רק את שכבת ה**טון**, שכבת ה**מרקם** חוזרת שלמה |
| **ניקיון עור** | סף כתמים גורף → מוחק נחיריים | סף שטח יחסי לפנים + **סף רזולוציה** (`faceTooSmall`) |

## 11. סטאק וטכנולוגיות

## 12. סדר בנייה (כל שלב = פרוסה אמיתית, נבנית כדי לשמור)

- **Phase 0 — בסיס** ✅ (בוצע): renderer + כלים גלובליים + מתכון + "החל על מסומנות" + POC עור.
- **Phase 1 — איחוד ה-Backbone** ✅ (בוצע): `ToolDef` אחיד + `toolRegistry` + `ToolInstance[]`; החלקת-העור היא **כלי במתכון** (לא דורס קנבס); pipeline: local-ai (מנוע, cached) → global (JS, חי); אצווה נושאת את המתכון המלא כולל AI. **ביצועי AI נמדדו: ~210–244ms לתמונה** (הסיכון שסומן — תקין). *(מעבר לנתיבי-קובץ נדחה ל-Phase 5/Electron; בדפדפן עדיין data URLs.)*
- **Phase 1.5 — גל הכלים הגלובליים** ✅ (בוצע): 7 כלים חדשים ברישום (תלת-מימדיות, צבעוניות, נקודת אור, גלואו, ציור שמן, חידוד) + הרחבת טון-וצבע ב-`whites`/`blacks`. הפאנל מרנדר **גנרי מהרישום** (קבוצות מתקפלות) — כלי חדש = שורה ברישום בלבד. מכסה 10/16 מרשימת הצלמת.
- **Phase 1.6 — MaskProvider + כלי AI שני** ✅ (בוצע): `engine/masks.py` (MediaPipe, 6 סוגי מסכות) + **טשטוש רקע**. שלב ה-AI ב-Editor הוכלל לשרשור **כל** כלי ה-AI לפי סדר. אומת על תמונה אמיתית: פילוח ~256ms, טשטוש מלא ~410ms, HTTP ~500ms. מכסה 11/16.
- **Phase 2 — שכבה 3** ⏳ *(הבא):* ספריית סגנונות בשם + אצווה דרך המנוע + ייצוא לדיסק + **מבחן parity** JS↔Python.
- **Phase 3 — כלי AI כאזרחים:** טשטוש רקע → עיניים → פצעונים.
- **Phase 4 — RAW** + חשיפה/WB אדפטיביים.
- **Phase 5 — אריזה:** Electron + הדלקת sidecar + מתקין.
- **Phase 6 — צפונה:** קאלינג, אלבום (מודולי החזון).
